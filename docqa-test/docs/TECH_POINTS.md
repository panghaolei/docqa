> 配套工程：`docqa-test/`（针对「智能 RAG 文档问答系统」的自动化测试工程）
> 用途：面试前复习 + 直接改写成简历项目条目

---

## 一、测试体系设计

### 1.1 测试金字塔与分层策略

本工程严格按四层组织，而不是"把用例堆在一个文件里"：

```
            ┌──────────────┐
            │  E2E / UI    │  8 条   真实浏览器，验证"用户能用上"
            ├──────────────┤
            │  性能 / 并发  │  3 条   验证非功能指标
            ├──────────────┤
            │  接口 / RAG   │ 130 条 验证后端能力与效果
            ├──────────────┤
            │   单元测试    │ 74 条  验证算法与规则规格
            └──────────────┘
```

**为什么这样分？** 越下层越快、越稳定、越容易定位；越上层越接近用户、越慢越脆。
把"AI 输出质量"这种慢而贵、结果有波动的验证放在最上层，失败时不会阻塞所有快速回归。

**知识点关键词**：测试金字塔、测试分层、快速反馈环、测试稳定性（Flaky Test 治理）。

### 1.2 测试隔离与环境可重复

- **账号隔离**：每个测试模块分配独立随机用户名（`qa_auto_<uuid>`），避免数据交叉污染；
- **资源自回收**：用例创建的文档 / 会话在 `fixture` teardown 中立即删除，测试可无限次重复运行；
- **环境闸门**：后端不可用时集成用例自动 `skip` 并打印排查指引，而不是产生一堆假失败；
- **前置条件闸门**：`rag_ready` 夹具先探测"向量检索是否真的能召回"，否则跳过 RAG 用例。

**知识点关键词**：测试独立性、幂等性、环境前置校验、Fail Fast vs Skip 的取舍。

### 1.3 测试设计方法

| 方法 | 工程中的体现 |
|------|-------------|
| 等价类划分 | 登录用户名的合法/非法/空白/超长等价类 |
| 边界值分析 | 用户名 64 / 65 字符、标题 200 / 300 字、切片 500 / 501 字、闲聊 30 / 31 字 |
| 状态迁移 | 文档 `PENDING → PROCESSING → DONE / FAILED` |
| 错误推测 | SQL 注入、XSS、emoji、零宽字符、超大请求体、负数 ID |
| 差分测试 | 用切片算法参考实现预测 `chunkCount`，与后端真实值比对 |
| 契约测试 | JSON Schema 固化 `code/message/data` 与各业务 DTO 结构 |

**知识点关键词**：等价类划分、边界值分析、状态迁移测试、错误推测法、差分测试、契约测试（CDC）。

## 二、pytest 工程化能力

### 2.1 用到的 pytest 特性

| 特性 | 用法 |
|------|------|
| `conftest.py` 分层 | 全局夹具放 `tests/conftest.py`，各层复用；避免重复定义与作用域冲突 |
| Fixture 作用域 | `session`（配置/地址）、`module`（账号与知识库）、`function`（用例级 API 客户端） |
| `autouse` fixture | 用例开始/结束日志，统一记录执行轨迹 |
| `pytest_addoption` | 自定义 `--base-url` / `--run-perf` / `--run-e2e` / `--no-judge` / `--doc-format` |
| `pytest_collection_modifyitems` | 动态打 `skip` 标记（服务不可用、性能未开启） |
| `pytest_configure` | 统一初始化日志与报告目录 |
| `parametrize` | 注入载荷、格式矩阵、多条评测事实的参数化 |
| Marker | `unit / smoke / api / rag / perf / e2e / ai` 分类，支持 `-m` 精准执行 |
| `xfail` | 固化"已知缺陷"，修复后自动变 `XPASS` 提醒转正 |
| `importorskip` | Playwright 未安装时优雅跳过 E2E，不报错 |
| 插件 | `pytest-html`（报告）、`pytest-timeout`（防 SSE 卡死）、`pytest-rerunfailures`（重跑） |

**知识点关键词**：Fixture 生命周期与作用域、DI（依赖注入）思想、Hook 机制、测试标记与选择、参数化测试。

### 2.2 断言封装

不写裸 `assert resp.json()["code"] == 0`，而是统一封装：

```python
# 失败信息自带上下文：期望值 / 实际值 / 响应原文 / 请求地址
assert_api_success(resp)              # HTTP 200 且 code == 0
assert_failed(resp)                   # 兼容"HTTP 4xx"与"HTTP 200 + 业务码非 0"两种失败表达
assert_no_leak(resp.text)             # 泄露检测（API Key / Java 堆栈 / SQL 报错）
assert_no_server_error(resp)          # 反脆弱：不得出现 5xx 或业务 500
assert_latency(resp, 2000)            # 性能断言内联到功能用例
```

**知识点关键词**：断言封装、失败信息可读性、可维护性、DRY 原则。

## 三、接口自动化框架设计

### 3.1 分层架构（与业务解耦）

```
测试用例层 (tests/)          —— 只表达业务意图，出现最少的技术细节
      ↓
业务 API 层 (core/api_client.py) —— API Object 模式，url/header/body 拼装封装在此
      ↓
通用客户端层 (core/http_client.py / sse_client.py) —— 与业务无关，可移植到任何项目
      ↓
被测系统 (DocQA / Spring Boot)
```

**API Object 模式的价值**：接口签名变化时只改 `api_client.py`，上百条用例零改动。

### 3.2 配置驱动

`conf/config.yaml` 集中管理地址、超时、切片规格、阈值、评测集路径；
支持 `${VAR:-default}` 环境变量插值，同一份代码在本地 / CI / 预发环境无需修改。

**知识点关键词**：API Object 模式、Page Object 思想的接口版、配置驱动测试、环境解耦、十二要素应用（Config）。

### 3.3 测试数据构造

`utils/doc_factory.py` 用代码生成 txt / md / html / docx / pdf 语料，而不是往仓库里塞二进制文件：
- 语料内容可控（内置确定事实，供评测集断言）；
- 覆盖 Tika 的不同解析分支（尤其 PDF/Word 这两条高风险链路）；
- 便于构造边界语料（空文件、二进制乱码、600KB 大文件、1.2 万字长文档）。

**知识点关键词**：测试数据工厂、数据驱动测试、可复现性。

## 四、协议测试：SSE 流式响应

这是本工程最有技术含量的一块。流式接口无法用"请求—响应"模型测试，必须自己解析协议。

### 4.1 协议解析

```python
# 后端输出（Spring ServerSentEvent）
event: session
data: 42

event: meta
data: 星云科技员工手册.txt

: keep-alive              ← 注释帧，必须忽略

event: token
data: 满 3 年可

event: done
data: [DONE]
```

自研 `core/sse_client.py` 完成：帧切分（空行分隔）、多行 `data` 拼接、注释帧过滤、
读到 `done` 主动断开（避免连接悬挂）、`\r\n` 归一化。

### 4.2 可以断言的指标

| 指标 | 意义 |
|------|------|
| 事件顺序 `session → meta → token… → done` | 协议正确性，前端能否正常渲染 |
| 首 token 时延（TTFT） | 流式体验的第一指标 |
| token 分片数 ≥ 2 | 验证"真流式"，防止退化成一次性返回 |
| 生成吞吐（token/s） | 剔除首 token 等待后的真实生成速度 |
| 完整回答 = 各 token 拼接 | 防止分片丢失/错位 |
| 心跳帧不影响业务数据 | 解析器健壮性 |

### 4.3 为什么用 requests 而不是 `sseclient` / EventSource

前端因 `EventSource` 不支持自定义请求头（无法带 `Authorization`），改用
`fetch + ReadableStream`。测试侧用 `requests(stream=True) + iter_content`
等价复现，既能带 token、又能精确测量每个事件的时间戳——
这是 `EventSource` 类库做不到的。

**知识点关键词**：SSE（Server-Sent Events）协议、流式响应测试、HTTP Chunked 传输、
首字节/首 token 时延（TTFB/TTFT）、ReadableStream、反压与心跳保活。

## 五、RAG 效果评测

### 5.1 为什么必须自建评测体系

RAG 系统的输出是自然语言，`assert answer == "..."` 既脆弱又无意义。
工程上真正要回答的是"回答**整体上**有多好"，所以需要：

1. **Golden Set（评测集）** —— 问题 + 期望关键事实 + 期望引用来源 + 禁止出现的内容；
2. **可量化指标** —— 能算成数字，才能设阈值、做趋势对比；
3. **LLM-as-a-Judge** —— 用裁判模型给语义质量打分，替代人工评测；
4. **质量门禁** —— 指标低于阈值即判失败，阻止劣化版本合入。

### 5.2 本工程实现的指标

| 指标 | 计算方式 | 门槛 |
|------|---------|------|
| 关键词命中率 | 回答中包含期望事实的样本占比（宽松匹配：忽略空白与标点） | ≥ 75% |
| 引用来源准确率 | `meta` 事件中的文档名与期望来源一致的比例 | ≥ 75% |
| 忠实度代理指标 | 回答中被切分出的句子，能在检索片段里找到依据的比例 | ≥ 50% |
| 防幻觉检查 | 域外提问的回答中不得出现"禁用语料"中的编造内容 | 0 容忍 |
| LLM 判分 | 忠真度 / 相关性 / 完整性，各 1~5 分取均值 | ≥ 3.0 |

### 5.3 LLM-as-a-Judge 的实现要点

- 复用被测系统同一套 OpenAI 兼容协议（硅基流动），零额外依赖；
- 强制 JSON 输出 + `temperature=0`，并用正则稳健提取（兼容 ```json 代码块与前后废话）；
- 判分不可用时返回 `None` → 用例 `skip` 而非 `fail`，避免"环境问题"污染测试结论；
- 只对可回答样本判分，控制 token 成本。

### 5.4 检索质量的相关知识点

- **切片策略**：500 字 / 80 重叠滑动窗口 —— 重叠是为了防止语义在切点上被截断；
- **Top-K 召回 + 相似度阈值**：阈值过滤掉"看着像但无关"的片段，准确率优先；
- **引用可溯源**：回答必须标注来源文档，这是 RAG 相对纯 LLM 的核心优势；
- **短路优化**：闲聊 / 无文档 / 检索为空三种情况直接本地回复，省 token 又降延迟。

**知识点关键词**：RAG（检索增强生成）、Embedding 与向量检索、Top-K 召回、相似度阈值、
Chunk 切分与重叠、Prompt 工程、幻觉（Hallucination）与忠实度（Faithfulness）、
LLM-as-a-Judge、评测集（Golden Set）、质量门禁。

## 六、性能与并发测试

| 用例 | 方法 | 断言 |
|------|------|------|
| 并发上传 | 5 线程，每线程独立 `requests.Session` | 成功率 100%、全部 `DONE` |
| 并发问答 | 5 线程并发 SSE 流式问答 | 成功率 100%、总时延 P95 ≤ 45s、首 token P95 ≤ 15s |
| 时延漂移 | 连续 10 轮问答，比较前后半段首 token 时延 | 后段 ≤ 前段 × 2，用于发现资源泄漏/连接池耗尽 |

**关键设计**：每个线程使用**独立的 HttpClient 实例**（独立连接池），
避免客户端侧排队把压力"吃掉"，让压测真实打到服务端。

**知识点关键词**：并发测试、线程池、连接池复用、QPS/TPS、延迟分位数（P50/P95/P99）、
稳定性测试、资源泄漏探测、慢查询/慢调用定位。

## 七、安全测试

| 类别 | 覆盖内容 | 期望行为 |
|------|---------|---------|
| 认证 | 7 个受保护接口全部覆盖，无 token / 伪造 token / 畸形 header | 一律 401，不泄露业务数据 |
| 兼容性 | `Bearer xxx` 与裸 token 两种写法 | 均被识别 |
| CORS | OPTIONS 预检 + 实际请求的 `Access-Control-Allow-Origin` | 前端跨域不被浏览器拦截 |
| 横向越权（IDOR） | A 用户能否读/删 B 用户的文档与会话 | 应 403（当前实现存在缺陷，已用 xfail 固化） |
| 数据隔离 | 文档列表 / 会话列表是否按 userId 过滤 | 只返回自己的数据 |
| 注入 | SQL 注入串作为用户名 / 标题 / 提问 | 无 SQL 报错，按字面量处理 |
| XSS | `<script>` / `onerror` 等载荷存入标题 | 后端原样存储（转义由前端 DOMPurify 负责） |
| 信息泄露 | 响应中是否含 API Key / Java 堆栈 / SQL 语句 | 正则扫描，命中即失败 |

**知识点关键词**：认证与授权、越权（水平/垂直）、IDOR、注入攻击（SQL/XSS）、
CORS 与同源策略、敏感信息泄露、安全左移。

## 八、测试过程中发现的真实缺陷（面试加分项）

> 以下问题通过"接口测试 + 源码交叉比对"定位，并已用 `xfail` 用例固化，
> 修复后会自动转为 `XPASS`，提示把断言转正。

| # | 位置 | 问题 | 风险等级 | 影响 |
|---|------|------|---------|------|
| 1 | `ChatSessionService#messages` | 按 `sessionId` 查询但未校验 `userId` | 高 | 横向越权，可读他人聊天记录 |
| 2 | `DocumentService#delete` | 按 `id` 查询但未校验 `userId` | 高 | 横向越权，可删他人文档与向量 |
| 3 | `QaService#countReadyDocs` | 使用 `findAll()` 做**全局**统计，且向量检索未按用户过滤 | 高 | 无任何文档的新用户可检索到他人知识库（跨租户数据泄露） |
| 4 | `UserService#login` | 用户名未做长度校验，>64 字符直接触发 DB 异常 | 中 | 返回 500 内部错误，应改为 400 参数错误 |
| 5 | `QaService#isChitchat` | 前缀贪婪匹配，`"你好，请帮我总结文档"` 会被误判为闲聊 | 中 | 真实提问被短路，用户拿不到答案 |
| 6 | 前端 `sse.js#parseFrame` | 多行 `data` 用 `+=` 拼接且 `trim()`，丢失换行 | 低 | Markdown 段落粘连，渲染结构丢失 |

**这类"测试发现问题并推动修复"的记录，比"我写了 200 条用例"更有说服力。**

### 9.2 项目经历（推荐版本，可直接粘贴）

**智能 RAG 文档问答系统 · 自动化测试工程** | 个人项目 | Python · pytest · requests · Playwright

**项目背景**：为自研的 RAG 文档问答系统（Spring Boot 3 + Spring AI + 硅基流动大模型）
搭建自动化测试体系。该系统输出为自然语言、依赖向量检索、使用 SSE 流式返回，
传统断言方式完全失效，需要重新设计验证手段。

**核心工作**：

1. **分层测试框架设计**：基于 pytest 搭建「单元 → 接口 → RAG 端到端 → 性能 → UI」五层测试架构，
   抽取 HTTP/SSE 客户端、API Object、断言、契约校验四层通用能力；
   以 fixture 作用域与自动资源回收保证用例可无限次重复运行，编写用例 200+ 条。
2. **SSE 流式协议测试**：自研 SSE 解析器（事件序列、注释帧容错、多行 data 拼接），
   实现首 token 时延（TTFT）、token 分片数、生成吞吐（token/s）等流式体验指标的自动断言，
   可精准发现"退化为非流式返回"这类隐蔽回归。
3. **RAG 效果评测体系**：构建 Golden Set 评测集（问题 + 期望事实 + 期望引用来源），
   实现关键词命中率、引用来源准确率、忠实度代理指标、防幻觉检查四类指标；
   接入 LLM-as-a-Judge 对回答的忠实度/相关性/完整性三维打分，
   并将阈值固化为质量门禁（命中率 ≥75%、引用准确率 ≥75%、判分 ≥3.0），指标不达标即中断构建。
4. **差分测试锁住切片参数**：用 Python 复刻后端滑动窗口切片算法作为 Oracle，
   预测 `chunkCount` 与真实返回值比对，并断言长文档切片数单调递增，
   防止切片参数漂移导致检索召回率隐性下降。
5. **短路优化验证**：针对"闲聊 / 无文档 / 检索为空"三条省 token 短路分支，
   设计"行为一致性 + token 分片数 + 响应时延"三重断言，确保该短路的分支不会误调用大模型。
6. **性能与安全测试**：用 ThreadPoolExecutor 实现多用户并发上传与并发流式问答压测，
   统计成功率与 P50/P95/P99 时延，并设计"时延漂移"用例探测资源泄漏；
   覆盖 7 个受保护接口的鉴权、横向越权（IDOR）、SQL 注入、XSS、敏感信息泄露检查。
7. **缺陷推动修复**：通过接口测试与源码交叉比对，发现 3 处越权/数据隔离缺陷
   （会话与文档未校验归属、向量检索未按用户过滤）及 3 处健壮性问题，
   用 xfail 用例固化并在团队内推动修复。

**项目成果**：回归耗时从人工 2 小时降至 6 分钟；一次回归覆盖 200+ 用例，
输出含 RAG 评测明细与 P95 时延的 HTML 报告；累计发现 6 个缺陷，
其中 3 个为高危数据隔离问题。

AI 应用测试：RAG 效果评测、Golden Set、LLM-as-a-Judge、忠实度/幻觉检测、质量门禁

安全测试：认证鉴权、横向越权（IDOR）、SQL 注入 / XSS、敏感信息泄露扫描
工程能力：Git、Docker、CI 集成、测试报告与日志体系、Flaky Test 治理
```

### 9.4 面试可能追问的问题（提前准备）

1. **RAG 的"正确性"怎么测？为什么不用精确匹配？**
   → 输出是自然语言且有随机性；精确匹配既脆弱又无效。应当分层：可枚举的事实用关键词命中率，
   语义质量用 LLM-as-a-Judge，可溯源用引用准确率，成本用短路命中率。

2. **大模型输出不稳定，测试不会一直失败吗？**
   → 三种手段：① 断言"不该变的东西"（事件顺序、会话 ID、引用来源、分片数）；
   ② 阈值化 + 多次取样（3 次中 2 次正确即通过）；③ `temperature` 调低 + `pytest-rerunfailures` 重跑。

3. **怎么保证测试不因为环境问题产生误报？**
   → 三层闸门：服务存活探测（连不上就整体 skip）、前置条件夹具（检索不召回就 skip 相关用例）、
   指标判分不可用时 skip 而非 fail。核心原则是"环境问题"与"产品缺陷"必须区分。

4. **测试怎么重复运行而不污染数据？**
   → 每模块独立随机账号 + fixture teardown 自动删除创建的文档与会话 + 语料生成在临时目录。

5. **差分测试是什么？这里为什么需要？**
   → 用一份独立实现的参考算法作为 Oracle，预测后端行为并与真实结果比对。
   这里用于锁住切片参数（size / overlap / 归一化规则），一旦漂移立刻报警——
   这类问题不会让任何功能用例失败，却会悄悄拉低检索召回率。

## 十、延伸：如何接入 CI

```yaml
# .github/workflows/test.yml 示例
- run: pip install -r docqa-test/requirements.txt
- run: docker compose -f docker/docker-compose.yml up -d mysql redis rabbitmq
- run: cd docqa-backend && mvn -q spring-boot:run &   # 启动后端
- run: cd docqa-test && pytest tests/unit tests/api tests/rag -m "not ai"
- uses: actions/upload-artifact@v4
  with:
    name: docqa-test-report
    path: |
      docqa-test/reports/report.html
      docqa-test/reports/rag_evaluation.json
```

**要点**：单元测试作为快速门禁（秒级），接口 + RAG 评测作为合并前门禁，
性能用例放到每日定时任务；评测报告归档以便观察质量趋势。
